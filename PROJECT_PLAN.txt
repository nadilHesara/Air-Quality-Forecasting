================================================================================
 PART A — WHAT IS ALREADY BUILT  (current state, verified 2026-07-02)
================================================================================

 The project is a working end-to-end ML pipeline. A single command
 (`python -m src.train`) goes from raw data to a trained, evaluated, and
 tracked model. A serving layer (API + dashboard) reuses the exact same
 feature code, and a GitHub Actions workflow retrains weekly.

 CURRENT HEADLINE METRICS (reports/metrics.json):
   - Model (LightGBM), held-out 90-day test:  MAE 3.31 | RMSE 4.53
   - Persistence baseline:                     MAE 3.47 | RMSE 4.90
   - Seasonal-naive baseline:                  MAE 5.43 | RMSE 6.96
   - Improvement vs persistence:  +4.5% MAE   (NOTE: this is small — see Phase 6)
   - Improvement vs seasonal-naive: +39% MAE
   - Data: 1,059 supervised rows, 26 features, 2023-07-20 → 2026-06-12

 [x] PHASE 0 — Project scaffolding & config
     - Central config.py (city, lat/lon, dates, API URLs, CV knobs, MLflow,
       retrain cron). Single source of truth; change city in one place.

 [x] PHASE 1 — Data ingestion
     - src/fetch_weather.py       : Open-Meteo historical weather (daily).
     - src/fetch_air_quality.py   : Open-Meteo air quality (hourly→daily).
     - src/build_dataset.py       : join on date, save training parquet.
     - APIs are free, no key required.

 [x] PHASE 2 — Feature engineering (leakage-safe)
     - src/features.py is the SINGLE SOURCE OF TRUTH for features, shared by
       training AND serving so production inputs can't drift.
     - 26 features: pollution context, 6 weather vars, PM lags (1/2/3/7/14),
       rolling mean+std (3/7/14/30), day-over-day diff, calendar features.
     - Documented leakage guarantee (all features use only info up to day t).

 [x] PHASE 3 — Training, validation & evaluation
     - src/train.py: one reproducible entry point (fetch→features→split→
       baselines→time-series CV→refit→evaluate once→persist→track).
     - Chronological split, expanding-window TimeSeriesSplit (no shuffling).
     - Two baselines (persistence, seasonal-naive) + % improvement.
     - Outputs: models/model.joblib, reports/metrics.json, results.md,
       shap_summary.png.

 [x] PHASE 4 — Serving & MLOps
     - src/inference.py : shared serving path (live fetch → features → predict).
     - src/api.py       : FastAPI (/health, /predict).
     - src/dashboard.py : Streamlit (headline metric + 30-day chart).
     - MLflow experiment tracking (local file store, params/metrics/artifacts).
     - .github/workflows/retrain.yml : weekly cron + manual retrain, commits
       refreshed model/reports, uploads mlruns/ as artifact, cron-drift guard.

 PART B — KNOWN GAPS & TECH DEBT  (fix opportunistically)
================================================================================

 These are real issues found in the current code. Several are addressed by the
 phases below, but list them here so they aren't forgotten:

 (D1) DEAD/DUPLICATE FEATURE CODE — HIGH PRIORITY CLEANUP.
      src/build_dataset.py still defines its OWN add_features()/add_target()
      with only the OLD 4 features (pm25_lag1, pm25_rolling7, day_of_week,
      month). Training no longer uses them (train.py calls features.py's
      build_supervised), so this code is misleading and can rot. Either delete
      these functions from build_dataset.py (keep only the fetch+join+save) or
      make build_dataset import from features.py. The README "Engineered
      Features" table also still lists the OLD 4 features — update it to match
      the real 26 in features.py.

 (D2) NO AUTOMATED TESTS. There is zero test coverage. The leakage guarantee,
      feature/column alignment, and baseline math are all asserted only by
      hand. This is the single biggest risk. See Phase 5.

 (D3) NO CI FOR CODE QUALITY. The only workflow is retrain.yml. No linting,
      no test run on push/PR. See Phase 5.

 (D4) MODEL BARELY BEATS PERSISTENCE (+4.5% MAE). For a portfolio/production
      story this is thin. Needs error analysis + tuning (Phase 6) or honest
      framing ("persistence is a strong baseline for next-day PM2.5").

 (D5) NO REPRODUCIBLE ENV PIN. requirements.txt uses >= ranges only; no lock
      file. CI could silently break on a dependency bump. See Phase 5.

 (D6) NO INPUT/DRIFT MONITORING. Retraining is blind — no check that new data
      is sane or that model quality hasn't regressed before committing.
      [FIXED 2026-07-02 by Phase 7: validate.py + drift.py + promotion_gate.py]

 (D7) SECRETS/ENV NOT DOCUMENTED for deployment; no Dockerfile. Phase 8.

 PHASE 6 — MODEL IMPROVEMENT: beat persistence convincingly
--------------------------------------------------------------------------------
 GOAL: Move the model meaningfully past the persistence baseline (currently
       only +4.5% MAE), or prove that gap is intrinsic and frame it honestly.

 TASKS:
   [ ] 6.1  Error analysis: plot residuals over time, by month/season, and vs
            actual PM2.5 level. Where does the model lose to persistence?
            (Likely: it under-predicts sharp spikes.) Save to reports/.
   [ ] 6.2  Feature experiments (guard each with the leakage test from 5.3):
              - Wind direction as sin/cos instead of raw degrees.
              - Interaction: humidity × precipitation; pressure change.
              - Longer/short lags; PM10-to-PM2.5 ratio; lagged weather.
              - Cyclical calendar encoding (month/day_of_year as sin/cos).
   [ ] 6.3  Hyperparameter tuning: proper time-series CV search (Optuna or
            sklearn) on the TRAIN POOL ONLY. Never touch the held-out test set.
            Log the study to MLflow.
   [ ] 6.4  Try alternative / ensemble models for comparison: quantile LGBM
            (for uncertainty), XGBoost, a simple ridge on lags, maybe a small
            SARIMAX baseline. Compare fairly in the existing metrics table.
   [ ] 6.5  Prediction intervals: switch to quantile regression (e.g. LGBM
            with objective='quantile' at 0.1/0.5/0.9) so the API/dashboard can
            show a range, not just a point.
   [ ] 6.6  Multi-horizon: extend from next-day to +1/+2/+3 day forecasts
            (either separate models or a recursive strategy). Optional/stretch.

 DONE WHEN: A documented experiment (in results.md / MLflow) shows either a
            clear MAE improvement over persistence, or a written justification
            that the remaining gap is intrinsic — plus prediction intervals
            available in the serving output.

 PHASE 7 — MLOps MATURITY: monitoring, validation & model registry
--------------------------------------------------------------------------------
 GOAL: Make automated retraining safe and observable — don't blindly commit a
       worse model.

 TASKS:  (completed 2026-07-02)
   [x] 7.1  Data validation before training: src/validate.py (hand-rolled, no
            pandera dep) — schema, row count, NaN budget, physical ranges,
            monotonic/unique dates, max gap, constant-feed check. Called by
            src/train.py before training; raises DataValidationError listing
            EVERY violation. Standalone: `python -m src.validate`. Knobs in
            config.py (MIN_TRAINING_ROWS, PM25_VALID_RANGE, ...).
   [x] 7.2  Champion/challenger gate: src/promotion_gate.py compares the new
            test MAE against the pre-training snapshot of metrics.json; the
            retrain job FAILS (nothing committed, old model keeps serving)
            if MAE regressed > config.PROMOTION_MAX_MAE_REGRESSION_PCT (5%).
            Verdict is appended to the GitHub step summary.
   [x] 7.3  MLflow Model Registry: src/registry.py registers each training
            run's model under the @staging alias (aliases are MLflow 3.x's
            replacement for the removed Staging/Prod stages); the CI gate
            then promotes @staging → @production. Serving loads the current
            production bundle when MODEL_SOURCE=registry (src/inference.py);
            without a registry backend everything degrades gracefully to the
            committed models/model.joblib, so model.joblib stays committed as
            the zero-infrastructure fallback until a remote server is set.
   [x] 7.4  Drift monitoring: src/drift.py. Training persists a MONTH-
            CONDITIONAL feature-distribution reference profile
            (reports/feature_reference.json — a June is compared with past
            Junes; a pooled reference would alarm every monsoon), scored with
            PSI over the last 60 days; plus recent live-vs-actual MAE vs the
            committed test MAE. retrain.yml runs it on fresh data BEFORE
            training and opens/updates a GitHub issue (label: drift) on
            alert — drift never blocks the retrain.
   [x] 7.5  Persistent tracking server: scripts/start_mlflow_server.{sh,ps1}
            run a SQLite-backed, registry-capable server; retrain.yml already
            forwards the MLFLOW_TRACKING_URI repo variable and (when set)
            promotes in the registry and skips the mlruns/ artifact upload.
            mlruns/ was already gitignored/uncommitted. NOTE: actually
            provisioning a CI-reachable server (self-host / DagsHub /
            Databricks) is an infra decision left to the operator — set the
            repo variable and everything activates.
   [x] 7.6  Backtesting harness: src/backtest.py walk-forward evaluation
            (train 365 d → forecast 30 d → roll forward, refit each step;
            24 folds, 693 out-of-sample predictions). Outputs
            reports/backtest.{json,md} + backtest_mae.png. FINDING: pooled
            MAE 4.23 vs persistence 4.16 (−1.7%), 11/24 folds beat
            persistence; RMSE slightly better (5.82 vs 5.90). The single
            90-day window's +4.5% was optimistic — reinforces the Phase 6
            honest framing (persistence is intrinsically strong; value-add =
            intervals + seasonal-naive win + RMSE).

 DONE WHEN: A retrain that produces a worse model does NOT get promoted ✓
            (gate fails the job); input data is validated ✓ (validate.py
            hard-fails training); model provenance lives in a registry ✓
            (when MLFLOW_TRACKING_URI is set; committed model.joblib remains
            as the documented zero-infra fallback).
